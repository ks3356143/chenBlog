- **批量改文件必须逐行保留原行尾**（2026-09-29 踩过）：本仓库 `core.autocrlf=true` 且**没有 `.gitattributes`**，
  而 git 索引里的行尾**本身就是混杂的**——实测一部分文件的 blob 存 CRLF、另一部分存 LF，工作区全是 CRLF。
  → 用脚本（node/sed）批量改写时要按 `(\\r?\\n)` 捕获再原样写回；改完先看 `git diff --numstat`，
  **每个文件应当只有你真正动过的那几行**。若出现"1 行改动变成 40/40"，就是行尾被整体翻转，立刻 `git checkout --` 回退换写法。
  反过来"把全项目统一成 CRLF/LF"这种好心想也别做，那会产生整文件重写式 diff。
  ⚠️ **2026-10-01 补：不只是脚本会翻，`Edit` 工具改一个混合行尾文件也会整片归一化成 CRLF**。
  本次改 `global.css`（blob 实测 112 CRLF + 64 LF）只想删 4 行，Edit 之后 `git diff --numstat` 变 61/65。
  → 修法：用 `git show HEAD:<file>` 取原始**字节**，按 `0x0A` 切块（块内保留 `\r`）、过滤掉目标块、
    `Buffer.concat` 原样写回，全程不做任何编码转换 → 净 diff 回到 0 增 4 删。
  → 判规模要用 `git diff HEAD --numstat`：`git reset --soft` 之后索引里还留着上一次那份翻好的文件，
    裸 `git diff` 比的是工作区 vs 索引，会给出一个误导性的数字。
  → 每次改完**先跑这一条再提交**，别等提交完才看到 diff 变大。
  ⚠️ 同一天还犯了一个**更狠的：读写编码不一致会直接写坏文件**。
  `readFileSync(f,"latin1")` 读、却 `writeFileSync(f,str)`（默认 utf8）写 → 非 ASCII 字节被重新编码，
  **中文注释全变乱码**，`global.css` 的 diff 从预期的 3 行炸成 16/14。
  → 铁律：**读什么编码就用什么编码写回**。本项目源码是 UTF-8 且中文注释极多，正常应当 utf8 读写；
    `latin1` 只适合只读地数列数/行尾，**绝不能顺手写回**。
  → 自查：改完跑 `grep -E "Ã©|å´|ä¸»|æå"` 扫一遍所有改动文件，命中即为乱码。
  提交前可用 `cp .git/index /tmp/tidx && GIT_INDEX_FILE=/tmp/tidx git add <文件>` 在**临时索引**里模拟暂存，
  确认 diff 规模没炸——这招不碰真索引，安全。

- ⚠️ **这台机器上 bash / node / PowerShell 三套路径与引号语义互不通用**，2026-09-29 一次会话踩 4 次，

    当时据此判定微信的两张图"不存在"，换成 `/d/` 才发现目录一直在（不过那两个文件确实已被清理，
    但**排除掉路径写法这个假信号之前，不能下"文件不存在"的结论**）。
  - **node 的 `fs` 不认 Git Bash 的 `/tmp`**，会解析成当前盘符下的 `E:\tmp` → `ENOENT`。
    跨工具传临时文件一律用 `path.join(process.env.TEMP, 'xxx')`，别在 node 里写 `/tmp/...`。
  - **PowerShell 命令串放进 bash 双引号会被 `$` 提前展开**：`$_.CommandLine` 变成 `extglob.CommandLine`，
    报一串 `CommandNotFoundException`，看起来像 PowerShell 坏了。整段要用**单引号**包，
    内层需要单引号时用 `'"'"'` 拼。
  - **写正则改文件前先确认实际缩进与行尾**：本仓库 `package.json` 是 2 空格 + LF，
    `src/utils/*.ts` 与 `src/config/*.ts` 是 4 空格，`.astro` 是 tab。
    凭印象写 `\t*` 去匹配 `package.json` 会**静默不匹配**（不报错，只是没改到）。
  - **含反斜杠的内容（Windows 路径）不要手抄进 `node -e` 脚本**：2026-10-09 同步手册时，
    `数据\生成\<项目>\` 的反斜杠被吃了两轮，而且我的**断言也跟着误判**（正则 `/数据\\生成/` 在
    bash 单引号 → JS 源码这条链上到底剩几个反斜杠，肉眼看不出来）。
    正确做法：① **直接从源文件那一行回填**（`fromSrc(行号)`，源文件里存着正确的字节）；
    ② 断言用 `const BS=String.fromCharCode(92)` 拼字符串 + `includes()`，**不要用正则字面量**；
    ③ 断言的期望值要算准"原有 + 新增"（那次文章里本来就有 9 个反斜杠，加 6 个应是 15，
    我按 6 断言结果自己把自己拦下来白查一轮）。最终仍以**浏览器 DOM 的 textContent** 为准。
  - **bash 的 `date` 在这台机器上取不到本地时间，别拿它写带时区的 frontmatter**（2026-10-10 发动态时踩到）。
    `TZ=Asia/Shanghai date "+%Y-%m-%d-%H%M%S"` 给的是 **`082224`**，同一时刻 `node -e "new Date()"` 是
    `16:22:45 GMT+0800`——Git Bash 没有 tzdata，`TZ` 指向的库文件名解析不到就**静默按别的时区出结果**，不报错。
    → 症状如果发生了会很难看：动态条目的 `published` 必须带 `+08:00`（五-23），
      照 bash 的时间写就成了「早上 8 点发的动态」，而**展示端也会跟着显示 08:22**（它只是把那个时刻按机区格式化）。
    → 铁律：**要时间戳一律 `node -e` 现取**（`new Date()` 本地读 + 自己拼 `+08:00`），文件名与 `published` 用同一个值。
      判别同类问题的通用办法：**凡是"跨工具拿环境量"（时间 / 路径 / 编码 / 用户名），两个工具各取一次再比对**，
      不一致时以 node/PowerShell 为准（它们走 Windows API），别信 bash 的模拟层。

## 七-补、停止规则（2026-11-05 立，硬约束）

> 起因：2026-11-05 连续两次在同一类任务上失控——上午 Twikoo 评估后空转 96 分钟，
> 下午出特效清单时又空转一个多小时、清单一个字没写。两次都不是命令卡死、不是循环重试，
> 而是「验证/调研动作在已足够的情况下继续自我复制」。这条规则就是为了在任何一步把它掐断。

### 四条判据（任一命中即执行）

1. **零增量三连** — 连续 **3 个动作**（命令 / 读文件 / 页面探测）**没有产出一句会出现在最终答复里的新句子** → 停。
2. **同类连击** — 同一个问题连续发起 **≥3 次**查询类命令（`grep` / `Select-String` / `Glob` / `curl` 页面探测），
   而**结论集合没有新增条目** → 第 3 次返回后立刻停。
3. **时限** — 纯调研 / 出清单类任务（不产出代码、不部署），从**第一次工具调用起满 15 分钟** → 停，
   输出已有部分并**写明卡在哪一条**。
4. **够用即写** — 已有材料**能填满用户要求的输出结构**（例如三档清单每档已有 ≥2 条）→ **直接开始写**，
   未核实项标注「未核实」，**不再查证**。

### 怎么执行（不是口号，是可判定的动作）

- 命中即 **停止一切新的工具调用**，把自己已有的结论按用户要的结构写出来。
- 用户问「为什么零产出」时，**列原始动作序列**（命令原文），不要概括成"在验证"。
- ⚠️ **触发信号是「我又想再查一个关键词」**，不是「我查错了」。**查到 0 命中 = 该特性确认不存在
  = 直接写进清单**，不要换个词再查一遍、不要为同一条特性换三种说法重试。

### 为什么必须这么硬

两次失控的共同结构：**任务在"已足够"之后没有终止条件** → 每个新动作都会发现"还有一项可以核" →
无限延续。所以判据必须绑在**动作计数与时间**上，而不是"我觉得差不多了"。

### 与「收尾铁律」的分工

- **收尾铁律**管「活干完了怎么交付」（清临时文件、更新 HANDOFF、推送）。
- **本规则**管「什么时候停止继续查/继续验」——**在交付之前**就该触发。
## 七-补二、效率纪律（2026-11-05 立，实测数据支撑）

> 起因：用户直接问「你干的有点慢，分析下主要用时在哪」。
> 我把 V0.1.86 那一批（四项改动，端到端 **41 分钟**）逐段量了一遍，
> 结论与直觉相反：**不是命令慢，是往返次数多 + 我自己写的空等 + 判断失误。**

### 一、实测基线（本机，2026-11-05）

| 操作 | 耗时 |
|---|---|
| 空 `pwsh` 一次（冷启动，**每次调用都付**） | **379 ms** |
| `npm run build`（astro + inject-preload + pagefind） | **9.8 s** |
| `astro preview` 启动到可访问 | **6.1 s** |
| 单次浏览器探测（起浏览器→开页→等→截图→关） | **3.1 s**（其中 `waitForTimeout` 空等 **1.4 s = 46%**） |
| 全站 51 页 × 3 断点扫描 | **72.5 s**（其中 300ms 固定等待 **46.8 s = 65%**） |
| `rg -l` 一次 | **53~61 ms** |
| `fd` 一次（warm） | **29~43 ms** |
| `Get-ChildItem -Recurse -Include` | **39~61 ms** |

### 二、四条纪律

**① 探测里禁止写死 `waitForTimeout`，改成等真实条件。**
`waitForSelector` / `waitForFunction`（等某个 class 出现、某属性变化、`getAnimations()` 结束）。
本批单次探测 3.1 秒里 1.4 秒是空等；全站扫 72.5 秒里 46.8 秒是空等 —— **这是最大的一块可省时间**。

**② 测一个效果前先隔离干扰源。**
本批 ⑪「浅色光晕」测了三轮才对，根因是**指针停在卡片上**，量到的是卡片 hover 辉光而非 spotlight。
正确做法：`page.addStyleTag` 先把无关的 hover / 动画屏蔽掉，再量。**一次隔离省两轮 build+preview+探测 ≈ 6~8 分钟。**

**③ 调参前先定判据。**
「亮一点 / 淡一点」必须先量化成可验收的数字（如「与深色版亮度差 ≈ 深色的 1/3」），
否则就会「改一版 → 渲染 → 看着还行 → 再改一版」无限循环。

**④ 查询优先走内置工具，不是因为快，是因为不踩坑。**
`pwsh` 里调 `rg`/`fd` 仍然要付 379ms 冷启动，**比 `Select-String` 还慢** —— 别为了「用 ripgrep」而多套一层 shell。
真正的收益是**内置 `grep` / `glob` / `read` 没有 PowerShell 的引号、中文路径、管道退出码问题**：
本批这类报错触发 **8 次**，每次重试 ≈ 一次完整往返 ≈ 25 秒 → **约 3.5 分钟**。
→ 判据：**只是「查内容 / 找文件 / 看某几行」→ 一律用内置工具**；
   `pwsh` 只留给「跑构建 / 起服务 / git / 部署 / 需要 PowerShell 对象管道」的场合。

### 三、真正的时间结构（本批 41 分钟）

| 项 | 分钟 | 占比 |
|---|---|---|
| 命令实际执行（build/preview/探测/扫描） | 3.3 | 8% |
| 读文件、查证、比较方案（**60+ 次往返**） | ~18 | 44% |
| 我自己写的固定等待 | ~8 | 20% |
| 判断失误多跑的轮次 | ~12 | 29% |

🔴 **通用结论：墙钟时间 ≈ 往返次数 × 单次往返成本，不是命令耗时之和。**
所以「怎么让单个命令更快」几乎没用；**怎么少做一次往返**才是杠杆。
具体就是上面四条：不空等、先隔离、先定判据、查询不绕 shell。

### 四、反例：什么时候**不**该省

- **构建/部署不能省步骤**：`npm run build` 那条链路（含 pagefind）必须完整跑，跳过就是线上 404。
- **全站扫描不能省**：51 页 × 3 断点是唯一能证明「没改坏别的页」的手段。
  但可以把 300ms 等待去掉、并只扫改动涉及的页型（完整扫留到发版前一次）。
- **视觉验证不能只靠数字**：本批 ⑫ 五张封面都是渲染出来逐张看过的，
  纯靠「文件生成成功」会漏掉 cover-7 那种「太亮像块白斑」的问题。

### 五、与「停止规则」的分工

- **七-补（停止规则）**：防止「已足够还继续查」。
- **本规则（效率纪律）**：防止「该快的地方慢」。
两条不冲突：**一条管上限（别无限查），一条管效率（别做无用功）**。
