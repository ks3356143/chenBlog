## 先说清楚这是什么

一句话：**它把「做一次软件第三方测评」从一堆散落的 Word/Excel，收敛成一条可追溯的关联链路，再从这条链路直接产出齐套的交付文档。**

一次测评真实长这样：研制方交来一批文档和被测件 → 按相关J标规范出测评大纲 → 评审 → 按大纲写测试说明、执行测试、记测试记录 → 发现问题开问题单 → 研制方改 → 回归 → 最后出测评报告。全程可能跨几个月，中间夹着多轮回归，最后要交 7 类文档，而且**每类文档的章节号、表格编号、需求追踪关系都必须对得上**。

这平台要解决的就是后面那句「必须对得上」。所以它不是「一个记录测试用例的工具」，而是**把文档结构反过来当成数据模型**：文档里有哪些章节、每章的数据从哪来、编号怎么推——先想清楚，再倒推需要哪些表、哪些字段、哪些校验。

先看一眼它长什么样：

![TestPlantAI 项目列表：12 个演示项目、4 张统计卡、5 个筛选维度，表格视图](/images/testplantai/01-list-table-full.webp)

![同一份数据的卡片视图：项目标识、类型角标、平台/级别/状态三个药丸、责任人、更新日期、规模](/images/testplantai/02-list-card-full.webp)

项目列表不只是「一张表」，它同时是**进度看板**：每行给 `测试项 24/30` 的录入进度环 + 轮次数 + 更新日期 + 状态药丸（编制大纲中橙 / 大纲已评审蓝 / 测试中青 / 已完成灰）。

## 一、功能：12 个模块，按「人怎么干活」排列

线上左侧菜单实际能点到的模块，按真实顺序分六层：

- **入口**：项目列表 / 新建项目
- **项目级**（全轮共享）：概览 / 被测对象 / 项目设置 / 时间管理
- **轮次级**（每轮独立）：轮次（管理 + 向导）/ 测试项 / 用例 / 问题单
- **追溯**：软件需求（树 / 矩阵 / 标注 / 覆盖 四视图）
- **交付**：文档（7 类 + 齐套性检查 + 模拟 Word 预览）
- **管理**：系统配置（10 项）

### 1.1 新建项目：把「终身不变」和「事后可变」分开

![新建项目 - 基本信息：项目标识、测试类型、平台、级别、软件类型、密级、安全等级、标签配置](/images/testplantai/03-new-basic-full.webp)

项目标识是 `R` + 年份后两位 + 序号（如 `RXXXX`），界面上明确标了**创建后不可修改**；测试类型/平台/级别三项标的是「管理员可修改」。这个区分不是随口标的——标识会进文档编号 `PT-RXXXX-TO`，改了全项目文档都得重编。

![新建项目 - 文档模板绑定：5 类文档各绑一份已发布模板，创建后终身不可更换](/images/testplantai/04-new-template-full.webp)

页面最下面这块是全站最反直觉的设计：**建项目时必须为 5 类文档各绑定一份已发布模板，创建后终身不可更换**。界面上写死了理由——「机构模板升级不影响存量项目」。这就是为什么它必须先有「文档模板管理」这个管理员模块：模板是项目的一等公民，不是运行时参数。

### 1.2 概览：一屏看清「这个项目还缺什么」

![项目总览：配置完善度 71%、5 段式进度条、三张信息卡、配置检查清单](/images/testplantai/05-overview-full.webp)

顶部右侧是「配置完善度 71% · 5/7 项已完善」，中间 5 段进度条（项目创建 → 大纲编制 → 大纲评审 → 测试执行 → 报告），已完成段打勾并带日期。下面三卡：基本信息 / 相关方 / 项目成员（3/4，未指定的角色标橙色"未指定"）。最底下两栏把 7 个必填数据块做成状态机，每项给「已填写 / 待填写 / 3/4 已指定」。

这个完善度不是装饰：7 个块缺一个，后面文档生成就一定缺章节，所以它被前置到概览页当 Checklist。

### 1.3 被测对象与引用文件：文档 §1.3 / §5 的数据源

![被测对象 - 接口说明：富文本 + 可编辑表格 + 图，表号「表5-5」是平台按章节位置算的](/images/testplantai/06-dut-interface-full.webp)

![被测对象 - 静态测试环境：软件项表 + 硬件固件项表，表号 5-6 / 5-7 自动生成](/images/testplantai/07-dut-static-full.webp)

注意表头直接写着「表5-5 XX03-XXX 外部接口信息表」「图5-2 ……接口示意图」——**编号是平台按章节位置推出来的，不是人手写的**。图可以直接 Ctrl+V 粘贴（转 base64 存进 assets[]）。

![项目设置 - 引用文件：分标准/管理文件、顶层技术文件、被测软件文档三类](/images/testplantai/08-ref-files-full.webp)

「引用文件」对应文档 §1.3，被拆成三段：① **标准/管理文件**（§1.3.1 表1-1，从管理员字典勾选）② **顶层技术文件**（§1.3.2 表1-2，立项任务书/总案文档/协作协议/指标要求这类研制方给出的输入，带标识版本、日期、来源单位）③ **被测软件文档**（§1.3.3 表1-3，分「研制方交付」和「平台生成」两段，前者是预置的 9 份标准文档清单）。这三段正好是测评大纲表 1-1 / 1-2 / 1-3 的数据源。

### 1.4 时间管理：只填 5 个锚点，其余全推导

![时间管理：5 个锚点时间 + 计划时间线（阶段/里程碑/产出文档/封面签署）](/images/testplantai/09-timeline-full.webp)

这是全站设计密度最高的一页。只让人填 5 个锚点（被测件接收 / 大纲编制开始 / 大纲评审 T 天 / 测试开始 / 测试结束），下面按阶段自动推导：每个阶段给起止日期 + 里程碑（大纲审查外部 / 说明评审 / 就绪评审）+ 产出文档（TO/TD/TN）+ **封面签署时间（拟制 → 校对 → 审核 → 批准，依次 +1/+2/+3 天）**。每行右侧有锁图标，锁住的推导值不会被重算覆盖。

### 1.5 软件需求：一棵树装下五层追溯

![软件需求 - 五层追溯树：来源文档 → 需求 → 测试项 → 用例 → 问题单，层级靠左侧色条区分](/images/testplantai/10-req-tree-full.webp)

左侧是一棵树：来源文档（文档 A V1.0，标发布单位）→ 需求（§3.3.1 某功能 · 功能 · V2.0 · 2 项）→ 测试项（XQ_SU_XXXX，带"有失败"红标）→ 用例（YL_SU_XXXX_001，✗）→ 问题单（PT_RXXXX_001，开放）。层级靠左侧色条区分（蓝→青→橙→红）。右侧是选中需求的详情：标识、来源、性质、可编辑描述（含需求条目表格 + 结构图）、关联测试项。

四个视图里，**矩阵视图**是给评审用的：

![追溯矩阵：一行一条需求，横向铺开来源→章节号→测试项→用例→问题单→通过率](/images/testplantai/11-req-matrix-full.webp)

顶部四个统计（需求总数 4 / 已关联测试项 4/4 / 用例总数 16 / 通过率 63%），下面每行给一个通过率（25% / 50%，分母是关联用例数）。**评审时一屏就能看出「哪条需求没被任何用例覆盖、哪条问题最多」。**

### 1.6 测试项：24 类字典，20 类可手建

![测试项 - 树视图 + 详情：hero、4 个数字卡、基本信息/受审文档/审查单三个 Tab、需求描述与通过准则](/images/testplantai/12-ti-tree-full.webp)

左侧按类型分组的树（文档审查 2 / 功能测试 5 / 接口测试 3），每个节点带 XQ 标识、优先级、完成度进度环。右侧是选中测试项的详情。

![新增测试项 - 类型字典弹窗：20 类分 5 组](/images/testplantai/13-ti-types-full.webp)

字典共 24 类（按测评大纲顺序），但弹窗只列 20 类——DC / SA / CR / CW 四类静态项不走这个入口。**为什么**：这几类的「形状」和功能测试完全不同，DC 用的是审查单检查项（reviewTargets）而不是测试子项（subItems），硬塞进同一个新增流程会逼用户填一堆无意义字段。它们由平台按规则自动创建：DC 每项目必建、默认带 3 张审查单和 14 项受审文档清单；SA/CR/CW 由 `ensureSAExists` / `ensureCRExists` / `ensureCWExists` 在进入测试项页时创建，且按平台分流——**SA 只在 CPU/桌面项目建，FPGA 平台不建**。

![测试项矩阵视图：同一套统计 + 矩阵表，看覆盖关系](/images/testplantai/14-ti-matrix-full.webp)

### 1.7 用例：详情页是「能直接进文档的一屏」

![用例详情：hero + 用例综述 / 用例初始化 / 前提和约束 / 测试步骤四段固定结构](/images/testplantai/15-case-detail-full.webp)

固定话术是刻意做的：初始化固定「软件正常启动，正常进入软件」，前提固定「外部设备正确运行，软件正常运行」，FPGA 项目的用例综述固定「见测试项描述」。这几段在真文档里 90% 是套话，每次重写是浪费——但**又不能没有**（评审会逐项看）。

![用例步骤表：序号 / 输入及操作 / 预期结果与评估标准 / 实际结果 / 通过与否](/images/testplantai/16-case-steps-full.webp)

步骤表是这一页信息量最大的部分：拖拽手柄、圆圈编号、实际结果整列可编辑、通过与否是绿/红药丸。还支持一套键盘流（工具条那个键盘图标会调出帮助面板，首次进详情还会自动弹一次，用 localStorage 的 `tiStepHelpShown` 记住"看过没"）：`Ctrl+Enter` 保存、`Tab` 下一字段（末行自动新增）、`Ctrl+D` 复制步骤、`Alt+R` 复制上一行、`Alt+↑/↓` 上下移动、`Space/Enter` 切换通过与否。一条用例几十步、一天录几十条，**纯鼠标点会把人废掉**，所以这页是按 Excel 手感设计的。

### 1.8 轮次：不是「所有数据的父节点」，是「范围切片 + 一对文档」

![轮次管理：轮次卡（时间窗口/被测件版本/测试项用例通过数/未完善警告/范围变化）+ 右侧轮次详情](/images/testplantai/17-round-full.webp)

左侧轮次卡上直接写「范围变化：第 1 轮 9 项 → 第 2 轮 4 项（回归 3 + 新增 1）」，右侧是第 2 轮详情：时间窗口、被测件版本 V1.0→V1.1、范围、文档标识 `PT-RXXXX-TD2-1.00 / PT-RXXXX-TN2`，下面「动态测试环境」可沿用上一轮快照。

这是全项目改过最多版的一处业务设计。旧版（老平台）是「轮次 → 需求 → 测试项 → 用例 → 问题单」的树，跑两轮之后树就大到没法用。现在的口径是：**需求树全局一棵**（不进轮次，各轮引用不复制）、**轮次只持有测试项/用例的实例**、**一轮 = 一对文档（TD{X} + TN{X}）+ 一份本轮数据快照**。

![新建轮次向导：一次把三组候选摆出来勾——上轮未通过用例、问题单影响域测试项、需求变更提醒](/images/testplantai/18-round-wizard-full.webp)

向导式建轮，一次把三组候选摆出来勾：① 上轮未通过用例（默认勾选，同测试项其余用例可选）② 问题单影响域测试项（默认全勾——"受影响 = 整项回归"）③ 需求变更提醒（提示性不强制）。

**为什么"受影响测试项默认全勾"**：上轮全通过的测试项，如果某个问题单的影响域指到它，说明代码动过，那它下面所有用例都得重跑，不能只挑失败的。漏跑一条"上轮通过"的用例，最后文档里那行的结论就没有依据。

### 1.9 问题单：一张单管到「回归闭环」

![问题单总览：6 个统计数字 + 两张交叉统计矩阵（TR 表31 / 表32）](/images/testplantai/19-issues-full.webp)

右侧两张矩阵——**按问题等级 × 问题类型**、**按等级 × 测试类型**——这不是给人看着玩的，**它们就是测评报告里的表 31 / 表 32**。平台上直接按交叉表统计，生成 TR 时整张表搬进去，不用人工数。

![问题单详情：面包屑 + hero + 问题属性（状态/等级/类型/来源/处理方式）+ 问题描述 + 研制方反馈](/images/testplantai/20-issue-detail-full.webp)

详情按「问题报告单」的字段顺序排。处理方式做成**多选且与"不修改"互斥**，因为真实问题经常既要改程序又要改文档。

### 1.10 文档生成：7 类文档 + 齐套性前置检查

![文档生成：左侧按类型分组（TO/TD/TN/TR/QT），右侧选中 TO 的详情、齐套性 9 项全绿、Word 模拟预览](/images/testplantai/21-docs-full.webp)

左侧按类型分组，每条给状态徽标（`✓ 已生成 V1.10` / `⚠ 未就绪（缺N项）` / `○ 可生成`）。右侧选中 TO：标识 `PT-RXXXX-TO-V1.10`、模板名与版本、签署自动处理、三个动作（已定稿 / 解锁定稿 / 下载 .docx），下面「齐套性 / 预览 / 状态表」三个 Tab。

齐套性 Tab 是最能体现「文档倒推数据」的地方：

![文档 TD2 详情：数据齐套性检查 9 项逐条打勾，缺项能点进对应录入页](/images/testplantai/22-docs-td2-full.webp)

9 项逐条打勾：项目基本信息 / 软件概述 / 接口说明 / 静态测试环境 / 动态测试环境 / 引用文件 / 时间管理 / 测试项列表 / 测试组织分工。缺项不是一句"数据不全"，而是**具体缺哪一块**，点进去跳对应录入页。

版本号规则是硬编码的：首次生成 `V1.00` → 评审后重新生成 `V1.10` → 再生成时弹窗让人选"保持"还是"升 V1.20"。重新生成覆盖旧版，同时在「文件状态表」追加一行。

### 1.11 系统配置：10 个管理员模块

![系统配置 - 文档模板管理：6 条模板（5 类正式 + 1 条草稿）、模板属性、文档大纲行树](/images/testplantai/23-admin-template-full.webp)

重点是**模板里存的是章节骨架，不是排版**。生成时先按骨架铺章节，再往每章灌数据。所以机构改模板（比如把"§4 测试项"从二级改成三级）不会破坏存量项目——项目创建时就绑死了自己那份模板版本。

其余九个：依据标准字典 / 相关方字典 / 项目管理 / 审查单配置 / 代码审查单配置 / 审查文档列表管理 / 枚举配置 / 权限管理 / 用户管理。

## 二、设计：四处和常规做法相反的地方

### 2.1 文档结构就是数据模型（最根本的一条）

常规做法是"先建业务表，再写导出模板"。这套反过来：**先把 7 份 docx 通读一遍，把每一章每一表列出来，再倒推数据模型**。设计文档里那份「逐章拆解」标了每份文档的页数与章节结构（测评大纲 64 页、测试记录 55 页、测评报告 31 页……）。

三个直接后果：

1. **字段命名跟着文档走**。数据库里的 `ImpactDomain` 直接对应问题单文档的「影响域分析」，`ClosureMethod` 对应「处理方式」。
2. **能提前发现「文档里有但没人想录」的章节**。比如回归轮的「软件更改部分（§3）」——要填版本对比 + 表31（更改类型/更改内容/影响域分析/影响用例）。这章不从问题单自动聚合，**必须人工填**，因为"改了哪些代码"只有研制方说得清。
3. **编号规则变成可推导的**。文档标识 `PT-RXXXX-TO` / `PT-RXXXX-TD2`、章节号 `5.2.1.1`、表号 `表5-5`、图号 `图5-2`，全由平台按"块插入位置 + heading_level_offset"算。

### 2.2 三层快照：多轮回归不污染已交付文档

测评做两三轮是常态。如果所有数据平铺在一个项目里，第二轮改环境描述，第一轮已交付的文档就对不上了。常规做法是"生成后不许改"——太硬，现实里环境确实会变。

它的解法是把数据分三层：

- **项目级**（全轮共享，不复制）：需求树 / 静态测试环境 / 相关方 / 被测对象 / 依据文件 / 锚点时间
- **轮次级**（每轮独立快照）：动态测试环境 / 测评数据 / 环境差异性分析 / 软件更改部分 / 本轮测试项·用例 / 本轮问题单
- **文档级**：生成时的数据快照 + 文件状态表

轮次创建时那三个环境块各给一个「沿用上一轮 / 空白新建」开关，**默认沿用**。换实验室、换硬件一键空白。

### 2.3 双层标识：回答「这个测试项历轮结果如何」

跨轮之后有个绕不开的问题：第 1 轮叫 `XQ_SU_0001` 的测试项，第 2 轮又带进来了，它还是同一个东西吗？

它的答案是**两层标识**：`LineageID`（逻辑 ID，项目级唯一）+ 轮次实例 ID。带入下一轮时继承逻辑 ID、保持同标识；自由新增的给新逻辑 ID、新标识。于是：

- 问题单关联、需求追溯、测评报告"历轮汇总" → 挂**逻辑 ID**
- 轮次内执行记录、TN{X} 生成 → 挂**轮次实例**
- 用例详情里嵌一个「上轮执行情况」折叠区，回归对照不用来回切轮次

没有逻辑 ID 的话，「某测试项经 3 轮测试、结论稳定」这句报告里的话，就没法从数据里查出来。

### 2.4 时间当推导结果，而不是人工填

就是 1.4 那一页的实现。推导规则：需求基线 = 被测件接收 + 3 工作日；产品基线 = 测评总结评审 + 7 工作日；封面签署依次 +1/+2/+3 天；问题单研制方确认 +5 工作日、回归日期必须落在下一轮窗口内；最末轮还有未闭环问题单 → 标"缺少回归轮次，无法闭环"。

**这解决了测评项目最常见的低级错误：封面日期和实际签署日期对不上、问题单回归日期落在轮次窗口外。** 这类错误评审必挑，但人工核几十份文档根本核不过来。

## 三、技术形态

- **三层解耦**：前端录入层（React 19 + Mantine + Tailwind v4 + Zustand + Vite 8）→ 数据层（Go + GORM + PostgreSQL JSONB）→ 文档生成层（Go 做 HTML→OOXML）
- **富文本统一 JSONB**：`{ title, body_html, body_json, assets[], heading_level_offset }`，前端 Tiptap 出 HTML/JSON 双输出，后端取 HTML 转 OOXML，assets 里的 base64 图解码写进 `word/media/`
- **文档生成不是"套模板"**：模板负责 75~85%（封面/表格/列表/附录/统计），富文本引擎负责 15~25%（软件概述/接口/环境描述这类长段落）。书签定位替换，不是字符串拼接
- **权限**：JWT + Casbin RBAC，角色 `super_admin / admin / user`
- **JSONB 预留扩展**：`Project.Extended` / `TestRound.Extended`，枚举走 EnumMeta 可增改

## 四、边界（写清楚，别夸大）

必须说清楚：**线上那个站是原型站，不是生产后端。**

- 跑的是 Vite 构建出来的静态原型，页面里是 **mock 数据**：12 个项目、演示项目 RXXXX 的 4 条需求 / 16 条用例 / 9 个问题单全是演示数据
- 原型**没有任何后端请求**——实测全部网络请求只有 html/css/js/字体/一张演示图，`fetch` / `XMLHttpRequest` 零调用；唯一用到的 localStorage 是 `tiStepHelpShown`
- 所以「下载 .docx」在原型里是模拟提示，不真产文件
- 设计文档的"当前实现状态"写得很老实：数据模型与部分 model 代码已完成，**后端 API 层、前端全部页面、文档生成引擎、Casbin 权限配置仍在待实现**

还有两处「没有的东西」，别硬凑：

- **没有独立的「接收文件 / 资料接收」模块**。研制方交来的东西分散在「项目设置 → 引用文件」（两张清单）和「时间管理 → 被测件接收日期」。没有"上传压缩包 → 自动解析归档"，文件本身也不进平台（存的是清单与元数据）
- **没有独立的「执行」页**。执行就在用例详情里：每步的「实际结果」+「通过与否」，用例级状态随步骤结果走，未通过再往问题单上挂

## 五、值得抄走的三条

1. **先读交付物，再建表。** 文档里有几章、每章数据从哪来——弄清楚了，数据模型基本就定了。反过来先建表、最后凑文档，一定出现"表里有字段但文档没处放"或"文档要的数表里没有"。
2. **多轮业务要区分共享数据与快照数据。** 判断标准：它变了，会不会让已交付的文档失真？会 → 快照；不会 → 共享。
3. **固定的套话就固定掉。** 用例初始化、前提约束这类 90% 不变的内容全部预设，把录入成本留给真正要人判断的字段。
