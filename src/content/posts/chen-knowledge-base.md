> 一个知识库真正的价值不在它装了多少，而在下一次要用的那五分钟里，能不能把那一条捞出来。

## 先说人

老陈平时写代码，也做界面。2026 年这一年，他大半的活落在 UI/UX 设计上：测试管理工具里的树形工作台、Windows 上的单人 AI 工作站、命令行工具的官网落地页、编辑器主题的皮肤改造。

这些界面彼此不共享一行代码，却共享同一批判断——卡片要不要圆角、主按钮该不该上整块渐变、深色底上灰字怎么分层、动效做到什么程度算吵。

麻烦在于，这些判断当时都想清楚了，却只活在「当时那个项目」里。换个项目从零再推一遍；三个月回来改，还得把当初的理由重新想一遍。他笔记里有一处就是这么长出来的：用户看到任务详情里的日期弹层，说「这个下拉框样式不太合适吧，炫酷点呗，有动效」，而问题不在配色——那些弹层根本不由页面绘制，Windows 在用系统外观画日历和下拉列表，CSS 只能改到输入框本体。这种判断不写下来，下个项目还得再撞一次。

2026 年 10 月 12 日，他给自己搭了这个库：Obsidian 编辑、git 管版本、纯本地，路径是 `E:\1.工作相关内容\★陈叫叫个人知识库`。

## 它现在的规模

2026-10-29 实测：

- **63 个 Markdown 文件**：37 个 README 索引、3 个模板、1 份规范、**22 篇正文笔记**
- 22 篇正文合计 **11.5 万字节**
- **43 个目录**，最深三层
- **20 次提交**，全部落在 17 天里

索引比正文还多，看着像过度设计。但这正是它最核心的取舍：**这个库是为「查」建的，不是为「存」建的。** 每层目录都有一个 README，写清这里放什么、不放什么、要什么来这里，所以读者（包括 AI）不用通读目录也能落到那一篇。

## 结构：先按用途切，再按粒度切

```text
0-收件箱/        没想好归哪的，先扔这儿，定期清空
1-开发技术/      前端（美观设计 · DSH界面 · React · Vue）· 后端（Go · Node · 数据库）
                 架构与数据 · 项目案例 · Word文档处理 · 工程效率
2-工作事务/      项目记录 · 流程与规范 · 问题与复盘 · 会议与决策
3-人生思考/      思考随笔 · 踩坑复盘 · 学习笔记 · 定期复盘 · 生活事务
5-灵感素材/      UI 截图 · 配色 · 好网站 · 组件案例
6-AI协作/        提示词库 · AI 工作流 · 工具对比
9-归档/          废弃与完结内容，只进不改
_模板/ _附件/    系统目录，不算分区
```

顶层按用途切，不按技术栈切——写代码的、上班的、想事情的，各归各的区，找东西时先想「这是哪一类事」。编号不连续，没有 4、7、8，好处是以后插新分区时不用给已有目录改名。

`1-开发技术` 底下才按技术分。最重的一块是 `前端/美观设计`：**17 篇、8.4 万字节，占全部正文的 73%**——这就是「目前大量在做 UI/UX 设计」在文件系统里的样子。

## 美观设计：按设计系统的标准分层

这一块没有按「按钮 / 表单 / 列表」随手分，而是照设计系统文档的通用层级切，另加一档外部案例。判据只有一条：**这东西管到多大。**

<div class="horizontal-scroll-container">

| 分档 | 管到多大 | 判定问句 | 篇数 |
| --- | --- | --- | --- |
| 基础 | 令牌与全局规则 | 是不是所有控件和页面都要遵守的值？ | 2 |
| 组件 | 单个可复用元素 | 能指着说就是这一个元素吗？ | 3 |
| 模式 | 组件组合出的任务解法 | 要记的是这些件怎么编排，不只是某一件长什么样？ | 7 |
| 页面 | 整屏 / 整站 / 整个应用 | 必须一屏以上同时看才成立吗？ | 4 |
| 案例 | 外部成品拆解 | 对象是别人的产品，且写明了实测依据吗？ | 1 |

</div>

依据是三条公开标准，不是自创：Styles / Components / Patterns 三分取自 [GOV.UK Design System](https://design-system.service.gov.uk/)，其中 Patterns 的定义是「Patterns often use one or more components and explain how to adapt them to the context.」；页面档对应 [Atomic Design](https://bradfrost.com/blog/post/atomic-web-design/) 顶端的 Templates / Pages；案例档单列则是个人库的额外需要——设计系统文档不收录「别人家怎么做」，但自己需要。

判定问句是关键。它把「这篇该放哪」从审美问题变成一道是非题，不用每次重新争论。

![极光HUD 工作台的设计评审板：上方四张解读卡，中间是 1440×900 的实际界面，下方是完整令牌表](/images/knowledge-base/01-hud-overview.webp)

> 页面档那一篇的配图：一份设计评审看板。四张卡分别讲结构、材质、信息、动效，中间是实际界面，底部是完整令牌表——一个方案要能被复述，才算写完。

五档各自的活儿，粗看一遍就知道这个库在收什么：

- **基础**（2 篇）：整站基调（令牌、直角约束、动效四层与总闸）、工作台的灰字三级分层与轻彩元数据
- **组件**（3 篇）：按钮的光泽与闪高、树组件的方向键行为、自动生成标识的冲突预览
- **模式**（7 篇）：连续录入的键盘闭环、树内搜索与最近访问、完整度筛选、主从详情轻审计、双卡片闪光引导、全局指针聚光、用自建弹层替换系统控件
- **页面**（4 篇）：极光 HUD 工作台、纯 CSS 离线氛围首屏、蓝调鎏光氛围的全屏推广、ChenMeridian 直角单色风
- **案例**（1 篇）：CommandCode 官网设计语言

## 入口只有一页

库最容易死的地方不是「东西不够」，是「东西都在但没人找得到」。所以他只留一个取用入口：`美观设计/README.md`。里面第一张表叫「按任务找」，拿着「我要做什么」直接对号：

<div class="horizontal-scroll-container">

| 我要做的 | 去哪篇 |
| --- | --- |
| 给整站定炫酷基调（配色 / 直角 / 动效节奏） | 基础/炫酷界面设计思路：霓虹渐变与动效配平 |
| 连续录入多条数据，别让手离开键盘 | 模式/连续录入表单键盘闭环 |
| 一键切到「待补齐 / 待确认」的记录 | 模式/工作台完整度筛选与待确认标识 |
| 做整屏工作台 / HUD 控制台 | 页面/极光HUD工作台视觉与动效方案 |
| 参考大厂官网是怎么做的 | 案例/CommandCode官网设计语言 |

</div>

整张表 **18 行**：17 条指向五档里的某篇笔记，剩下 1 行把「给 DSH 做皮肤」分流到独立区域——那类资料绑定宿主版本、不可移植，不参与五档。

单一入口之外还有一条硬规矩写进规范里：**不要整目录通读**。先定位到一篇、只读那一篇，需要细节再顺「相关笔记」跳。这条对人和对 AI 都成立，因为上下文窗口和注意力一样贵。

## 光找到一篇还不够

只拿一档会瘸腿：只抄组件，好看但不成体系；只抄页面，体系对了但细节粗糙。所以入口页的第二条路是「按颗粒度拼装」——一条完整的设计知识，四档各取一点：

<div class="horizontal-scroll-container">

| 步骤 | 取哪档 | 取什么 | 产出 |
| --- | --- | --- | --- |
| 1 定规则 | 基础 | 炫酷界面设计思路 | 令牌、直角约束、动效四层与「可关闭」 |
| 2 定整屏 | 页面 | 极光 HUD / 纯 CSS 氛围首屏 | 布局骨架、氛围浓度、辉光预算 |
| 3 定手感 | 组件 | 按钮光泽闪光 | 主操作的高光质感（唯一用整块渐变的地方） |
| 4 定反馈 | 模式 | 全局指针聚光表面 | 卡片跟手微光；性能敏感时换成一次性高光 |
| 5 收口 | 基础 | 回看第 1 步的验证清单 | 辉光预算、动效总闸、减少动效 |

</div>

三条硬约束是从各篇里共同抽出来的，抄界面时先守住它们再谈风格：

1. **渐变垄断**：整块渐变只给主操作，其余用极淡辉光与语义色。
2. **直角骨架**：结构件圆角归零，只有控件用全圆角胶囊。
3. **动效可关**：常驻动画幅度极小，必须给总闸并尊重 `prefers-reduced-motion`。

![极光 HUD 工作台实际界面：深靛黑底 + 左侧会话树 + 中间日程 + 右侧 CLI 会话面板](/images/knowledge-base/02-hud-detail.webp)

> 三条约束落到真实界面上长这样：底色是深靛黑而不是纯黑，紫青做数据色、琥珀只标「现在 / 待确认」，渐变只出现在「开始专注」一个按钮上。

## 案例档：抄手法，不抄令牌

案例档只有 1 篇，但它是整条链路里最容易被误用的一档。CommandCode 官网那篇的写法是：实地抓取、截图、量数值，然后明确写清哪几条可以带走、哪几条不能。

![CommandCode 官网的「Without Taste / Mmmmm. Taste.」对照区](/images/knowledge-base/03-commandcode-compare.webp)

> 对照区：左边是别的编程 agent 一路试错，右边是「已经学会你的口味」的版本。整屏只有一处紫色，其余全是黑白灰与 1px 发丝线。

可以带走的是手法：一套 1189px 容器 + 左右竖列线，把整页切成格子；0 圆角做骨架、100px 圆角做控件，用反差同时拿到「工业图纸的硬」和「控件的亲和」；深度只靠 1px 线创造，不用阴影和卡片底色；紫色是唯一色彩事件，所以满屏色块也不吵。

不能带走的是令牌：色值、圆角数值、间距必须按目标品牌重算。规范里就一句——**抄手法，不抄令牌**。

## 写笔记的规矩比笔记本身重要

库能维持，靠的不是自觉，是几条可执行的规矩：

- **frontmatter 六字段**：`title` / `type` / `tags` / `status` / `created` / `updated`，`type` 五选一（设计思路 / 踩坑记录 / 人生思考 / 工作笔记 / 索引），`status` 四选一（草稿 / 成稿 / 已验证 / 已废弃）
- **文件名 = 标题**，不加日期前缀——日期在 frontmatter 里，不写在文件名上
- **同一主题有新认识就地更新**，不新建 `xxx-最终版`、`xxx2`；跨档升级时移动文件并修正互链，不保留旧副本
- **设计类笔记四段式**：适用场景 / 核心原则 / 实现建议 / 验证清单，末尾再挂 2–3 篇相关笔记，**每篇写一句为什么相关**，不放裸链接
- **归档区只进不改**：`status` 标废弃或项目完结，整体移进 `9-归档/`，需要时移回对应分区就复活

其中「相关笔记要写为什么相关」这条最不起眼，但它决定了这个库是一个知识网还是一个文件夹堆。

## 让 AI 也吃这一套

2026 年写界面，AI 是实际参与者。所以库里有两条对称的约定，各是一段可以直接粘进其他项目 `CLAUDE.md` / `AGENTS.md` 的模板：

- **取用规则**：做界面前先查库；入口只有一页；先按任务表定位到一篇、只读那一篇；要成体系时按颗粒度取；案例只抄手法；库里没有的再自己设计，做完把可复用部分回写。
- **采集规则**：其他项目里的 AI **只负责采集**——往 `0-收件箱/` 写一条记录，只写三段（来源、场景、想法，含关键代码），不分类、不动别的文件；分类、补 frontmatter、更新索引、提交推送由库会话做。

这个分工值得照抄：**采集端只管不丢，整理端只管不脏。** 让每个项目的 AI 都去维护目录结构，结果一定是二十套互相打架的分法。

## 现在到哪一步了

账要算清楚，才看得出这套结构成立在哪、没成立在哪：

- **美术/界面这块基本成型**：17 篇齐了五档，两条取用路径都能走通，每篇都有验证清单
- **其他技术方向只有零星几篇**：后端 Go 1 篇（不可逆批量删除）、Word 文档处理 1 篇（docx 编号系统探测与离线验收）、AI 协作 1 篇、DSH 界面 2 篇（独立成区，不进五档）
- **`2-工作事务` / `3-人生思考` / `5-灵感素材` 目前只有骨架 README**，还没有内容
- 20 次提交、17 天，从「全栈长期设计思路 V1」那篇开始，中间重构过两次分档

也就是说，它现在不是「一个全栈知识库」，而是**一个以 UI/UX 设计为主干、其他方向先搭好架子的库**。这个状态是故意的：先把最常用、复用成本最高的那一块做到能查能用，再往里长别的。

## 能抄走的是什么

如果要照着搭一个自己的库，这四步比目录结构本身更值得抄：

1. **先定档**：拿一句判定问句把内容切开（管到多大 / 用在哪一层），不要按主题随手建目录
2. **再定入口**：同一个领域只留一页入口，入口里第一张表必须是「我要做什么 → 去哪篇」
3. **再定配方**：写清「一条完整知识 = 哪几档各取一点」，否则取用的人只会拿最顺手的那一档
4. **最后定采集闭环**：给写入端一个唯一落点（收件箱）+ 极简格式，把分类权收归整理端

剩下的都是细节。库的价值从来不在结构漂亮，而在下一次要用的时候，五分钟之内能不能落到那一篇。
